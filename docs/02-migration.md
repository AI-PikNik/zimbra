# Миграция Zimbra со старого сервера на новый

Перенос выполняет скрипт [`scripts/zm-ldap-migrate.py`](../scripts/zm-ldap-migrate.py). Он работает на **новом** сервере от пользователя `zimbra`, читает старый сервер по LDAP и REST и ничего на нём не меняет. Сторонние Python-модули не нужны: достаточно `python3` из состава ОС.

Проверено при переносе с Zimbra 10.0 FOSS (RHEL 8) на Zimbra 10.1 FOSS (Maldua, Ubuntu 24.04): 7 доменов, около 190 учёток, 2 млн писем.

Адреса и имена в документе — примеры: `mail-old.example.com` — старый сервер, `mail-new.example.com` (`10.0.10.10`) — новый.

## Что переносится

| Режим | Что переносит | Как |
| --- | --- | --- |
| `--ldap` | классы обслуживания (COS), домены, учётки с прежним `zimbraId` и хэшем пароля, подписи, персоны, внешние ящики (datasources), алиасы, списки рассылки, глобальные делегированные права | LDAP старого → `zmprov` и `ldapmodify` нового |
| `--data` | почта, контакты, календари, задачи, портфель | REST: выгрузка `tgz` со старого, загрузка на новый |
| `--reindex` | поисковый индекс ящиков | `ReIndexRequest` на новом сервере |

Пароли у пользователей не меняются: переносится хэш. Прежний `zimbraId` сохраняет общие папки и делегированные права между ящиками.

**Не переносится:** системные учётки (spam, ham, virus-quarantine, galsync), ресурсы календаря, настройки серверов и глобальная конфигурация. Учётки синхронизации адресной книги (GAL) нужно создать заново: команды скрипт выводит в конце режима `--ldap`.

## 1. Подготовка

**На новом сервере** (от root):

```bash
install -d -o zimbra -g zimbra -m 700 /opt/zimbra/migration
cp zm-ldap-migrate.py migrate.conf.example /opt/zimbra/migration/
chown zimbra:zimbra /opt/zimbra/migration/*
```

**Файл настроек** (от zimbra):

```bash
cd /opt/zimbra/migration
cp migrate.conf.example migrate.conf && chmod 600 migrate.conf
nano migrate.conf      # если кириллица отображается неверно: export LANG=C.UTF-8
```

| Секция | Что указать | Где взять (на старом сервере, от zimbra) |
| --- | --- | --- |
| `[old]` | `ldap_url`, `bind_dn`, `bind_pw` | `zmlocalconfig -s ldap_url zimbra_ldap_userdn zimbra_ldap_password` |
| `[old_rest]` | `url` (https://<старый>:7071), `admin`, `password` | глобальный администратор старого сервера |
| `[migrate]` | `exclude_domains`, `workdir`, `chunk_mb` | домен самого старого сервера обычно исключается |

Скрипт откажется работать, если файл настроек доступен кому-то кроме владельца.

**Сеть:** с нового на старый должны быть открыты TCP 389 (LDAP, STARTTLS) и TCP 7071 (REST и SOAP администратора).

**Ограничение частоты запросов.** Встроенный DoS-фильтр Zimbra отвечает `HTTP 429` на частые запросы. Адрес нового сервера добавляется в исключения **на обоих серверах** (от zimbra):

```bash
# на старом
zmprov mcf +zimbraHttpThrottleSafeIPs 10.0.10.10
zmmailboxdctl restart
# на новом
zmprov mcf +zimbraHttpThrottleSafeIPs 10.0.10.10 +zimbraHttpThrottleSafeIPs 127.0.0.1
zmmailboxdctl restart
```

Без исключения на новом сервере консоль администратора во время переноса показывает `CSFE_SVC_ERROR, HTTP response status 429`.

**Справка:**

```bash
python3 zm-ldap-migrate.py                      # что нужно подготовить
python3 zm-ldap-migrate.py -c migrate.conf      # все ключи и примеры
```

## 2. Ключи

| Ключ | Назначение |
| --- | --- |
| `--ldap`, `--data`, `--reindex` | режим; можно несколько, выполняются в порядке LDAP → данные → переиндексация |
| `--verify` | сверка, ничего не меняет. Без режима — сверка LDAP и данных |
| `--dry-run` | только план, ничего не меняет. Без режима — план LDAP и данных |
| `--domain D` | только домен D (можно несколько раз или через запятую) |
| `--only A` | только учётка A (можно несколько раз) |
| `--types` | для `--data`: `all` (по умолчанию) или через запятую `message, contact, appointment, task, document` |
| `--sync` | для `--data`: почта — только новое с прошлого переноса |
| `--force` | для `--data`: всё заново |
| `--diff-only` | для `--data`: только ящики, где количество на старом и новом не совпадает |
| `--yes` | не спрашивать подтверждение перед очисткой контактов и календарей на новом |
| `--workers N` | параллельных ящиков, по умолчанию 4 |
| `--chunk-mb N` | ящики больше N МБ переносятся частями: почта по годам |
| `--keep-files` | не удалять выгруженные архивы (для разбора проблем) |

## 3. Этапы

### Этап 1. LDAP

```bash
python3 zm-ldap-migrate.py -c migrate.conf --ldap --dry-run    # план
python3 zm-ldap-migrate.py -c migrate.conf --ldap --only test@example.com   # одна учётка для проверки
python3 zm-ldap-migrate.py -c migrate.conf --ldap
python3 zm-ldap-migrate.py -c migrate.conf --ldap --verify
zmmailboxdctl restart
```

Повторный запуск безопасен: существующие объекты не создаются заново, атрибуты перезаписываются значениями со старого сервера. После переноса проверить вход тестовой учёткой со **старым** паролем и создать учётки GAL командами из вывода скрипта.

### Этап 2. Первичный перенос данных

Старый сервер продолжает работать, пользователи его не замечают.

```bash
python3 zm-ldap-migrate.py -c migrate.conf --data --dry-run
python3 zm-ldap-migrate.py -c migrate.conf --data
python3 zm-ldap-migrate.py -c migrate.conf --data --verify
```

Если сверка показала расхождения, кроме мелких (новая почта на старом сервере):

```bash
python3 zm-ldap-migrate.py -c migrate.conf --data --force --diff-only
```

### Этап 3. Переиндексация

После загрузки поиск по письмам может не находить перенесённое, пока ящик не переиндексирован:

```bash
python3 zm-ldap-migrate.py -c migrate.conf --reindex --workers 2
```

Переиндексация нагружает диск и процессор; 2 потока — разумный компромисс.

### Этап 4. Переключение

Пока пользователи работают на старом сервере:

```bash
python3 zm-ldap-migrate.py -c migrate.conf --ldap                     # изменения учёток за время подготовки
python3 zm-ldap-migrate.py -c migrate.conf --data --sync --reindex    # новая почта, контакты и календари заново
```

Затем переключить приём почты на новый сервер (PMG Default Relay, DNS), дождаться пустой очереди на старом (`postqueue -p`) и выполнить финальный проход:

```bash
python3 zm-ldap-migrate.py -c migrate.conf --data --types message --sync --reindex
python3 zm-ldap-migrate.py -c migrate.conf --verify
```

**После того как пользователи перешли на новый сервер, `--sync` и `--force` для контактов, календарей, задач и портфеля не запускать:** очистка удалит то, что пользователи уже создали на новом сервере. Финальный проход выше переносит только почту (`--types message`) — это безопасно.

## 4. Повторные запуски `--data`

Даты переноса по каждому ящику и типу хранятся в `workdir/data-state.json`. Этот файл не удалять: по нему скрипт пропускает уже перенесённое и находит дату для `--sync`.

| Команда | Почта | Контакты, календари, задачи, портфель |
| --- | --- | --- |
| `--data` | только ящики, где ещё не переносилась | только ящики, где ещё не переносились |
| `--data --sync` | новое с прошлого переноса | очистка на новом и загрузка заново |
| `--data --force` | полностью (повторы Zimbra отсеивает) | очистка на новом и загрузка заново |

Дублей нет ни в одном режиме. Почту Zimbra при загрузке с `resolve=skip` не дублирует; контакты и календари она так не распознаёт, поэтому скрипт их всегда очищает на новом сервере и загружает целиком. Очистка выполняется только после успешной выгрузки со старого: если старый сервер недоступен, на новом ничего не удаляется. Перед очисткой скрипт спрашивает подтверждение (без вопроса — `--yes`).

## 5. Как читать вывод

```
[ 26/184  14%] OK ✗   user@example.com   458 КБ  почта 7403≠7406 ✗ · контакты 66 ✓ (+66)  [очищено на новом: 105]
```

| Фрагмент | Значение |
| --- | --- |
| `26/184 14%` | порядковый номер завершённого ящика (ящики идут параллельно, поэтому не по алфавиту) |
| `OK` | без ошибок. Также: `ОШИБКА` (текст строкой ниже), `ПРОПУЩЕН` (уже перенесено), `СОВПАДАЕТ` (`--diff-only`), `НЕТ НОВЫХ`, `ПРЕРВАН` |
| `✗` после статуса | хотя бы у одного типа количество не совпадает |
| `458 КБ` | передано этим запуском, а не размер ящика |
| `почта 7403≠7406 ✗` | на новом 7403, на старом 7406 |
| `(+66)` | изменение количества на новом за этот запуск |
| `[очищено на новом: 105]` | удалено на новом перед загрузкой |

Раз в минуту выводится общий прогресс:

```
… 0:12:00 | готово 35/184 | передано 2,1 ГБ, 10,5 ГБ/ч | 6% объёма, осталось ~3:05:10 | в работе: user1 ⇡360 МБ/468 МБ · user2 почта 2015 ⇣133 МБ
```

`⇣` — выгрузка со старого, `⇡` — загрузка на новый, `почта 2015` — часть большого ящика, `индекс 50/115` — переиндексация. Оценка оставшегося времени появляется после 3 % объёма и 10 минут работы.

Почта считается по всем папкам без собственного вида (Входящие, Отправленные, Черновики, Спам, Корзина и пользовательские папки). Небольшая разница (1–15 писем) на работающем старом сервере — обычно новая почта, её добирает `--sync`.

**Файлы в каталоге запуска** (`workdir/<дата-время>/`): `migrate.log` — полный журнал, в том числе число элементов в каждом выгруженном архиве; `data-report.csv` — количество по каждому ящику и типу; `verify-report.txt` — расхождения LDAP.

**Прерывание:** одно нажатие Ctrl+C. Скрипт перечислит незавершённые ящики и подскажет, что запустить для них повторно.

## 6. Известные проблемы

| Симптом | Причина | Решение |
| --- | --- | --- |
| `HTTP 429` при переносе или в консоли администратора | DoS-фильтр Zimbra | `zimbraHttpThrottleSafeIPs` на обоих серверах (раздел 1) |
| `INVALID_PASSWORD` при создании учёток | политика паролей COS | скрипт создаёт временный пароль по правилам COS, затем записывает хэш старого |
| `HTTP 401` при загрузке | загрузка шла на публичное имя, которое в DNS указывает на старый сервер | скрипт загружает напрямую на имя нового сервера (`zimbra_server_hostname`) |
| Контакты на новом меньше, чем на старом | несколько типов одним архивом и/или оборванная выгрузка (Zimbra отдаёт `200` и обрывает поток) | каждый тип выгружается отдельно, архив проверяется целиком до загрузки, при обрыве — повтор. Исправить старые расхождения: `--data --force --diff-only` |
| На новом меньше писем, разница — ровно содержимое корзины (`zmmailbox -z -m <ящик> gaf`, строка `/Trash`) | выгрузка Zimbra (REST tgz) по умолчанию пропускает корзину и спам, как и обычный поиск | скрипт выгружает их отдельной частью «почта: корзина и спам» (`under:trash OR in:junk`). Довезти в ящики, перенесённые старой версией скрипта: `--data --types message --force --diff-only` |
| Поиск не находит перенесённые письма | индекс не построен | `--reindex` |
| `Permission denied` на каталог | `/opt/zimbra` принадлежит root | `install -d -o zimbra -g zimbra -m 700 /opt/zimbra/migration` |
| Кириллица в `nano` нечитаема | локаль `C` | `export LANG=C.UTF-8` |

## 7. Чек-лист переключения

- [ ] TTL DNS-записей почты снижен до 300 секунд за сутки
- [ ] `--ldap --verify` без расхождений; вход со старым паролем работает
- [ ] Учётки GAL созданы
- [ ] `--data --verify`: крупных расхождений нет
- [ ] `--reindex` выполнен, поиск работает
- [ ] `--ldap` и `--data --sync --reindex` перед переключением
- [ ] PMG Default Relay → новый сервер; очередь старого пуста
- [ ] Финальный `--data --types message --sync --reindex`
- [ ] DNS → новый сервер, сертификаты выпущены
- [ ] На старом закрыты 25/465/587; сервер хранится 2–4 недели на случай отката
